## Two patches are deliberately left out

**`patch_year_built_precision_2026-08-29.csv` — found stale while building this, and it would
have destroyed content.** It sets `year_built_precision` to the bare token `unknown` on three
rows that now carry a real qualification:

| Row | live today | the patch |
|---|---|---|
| Darbar Abul Muali Qadri | `Uncertain — field value is a Hijri day-and-year, not a building date` | `unknown` |
| Darbar Malik Ahmad Ayaz | `Uncertain — date derived from the figure's death date; calendar era not stated` | `unknown` |
| Shrine of Bibi Pak Daman | `uncertain / referent disputed` | `unknown` |

Three things say no and they agree. RULE 2 — those sentences *are* the qualification, and the
rule's worked example is exactly a date field that may refer to a death rather than a
construction being **correct** and not to be tidied. `src/lib/data/yearPrecision.ts` supports
free-form values **by design**: its docstring says such qualifiers "return null and are rendered
verbatim in `<bdi>`, like the source notes", naming `uncertain / referent disputed` as the
example. And the ruling of **5 September**, six days after that patch, writes prose into this
very column for Shah Jamal and Peer Makki — while
`patch_field_survey_orphans_2026-09-05.INSTRUCTIONS.md` cites Malik Ahmad Ayaz's value, one of
the three above, as the shape it is imitating. Applying the older patch would delete the model
the newer ruling was built on.

**`patch_provenance_badges.csv`** — excluded for the reason `build_final_import.py` recorded on
16 August: generated before three enrichment passes added citations to rows it had already
scored, so it regresses correct `info_level` values to stale ones. 58 of its 167 rows disagree
with the live sheet. Re-deriving the badges is its own job with its own instrument.

## `data/import_2026-09-05.csv` is not this file, and is not a base for it

It reads like a consolidated current state and it is a **mirror of the un-patched sheet** — it
carries `category` = `Islam` for two rows and `Sufi shrine (Islam)` for a third, verbatim, the
same three values `data:check:live` fails on. A "Replace current sheet" import of it applies
none of the other patches. This builder never reads it.

## The invariants, and the one that changed the output

Eleven, all refuse-to-write (RULE 4). Row count and id uniqueness; every cell no patch claims
byte-identical to the live fetch (7,475 of them checked); no `Description` touched; balanced
asterisks, no newline lost, no soft wrap gained on all 61 written cells; every `category` and
`status` inside its schema; every written `site_type` a short term with its prose preserved;
the header shape.

**INV-11 is new and it is the one that earned its place.** It refuses any write that flattens a
multi-word qualification into a bare token *unless the sentence lands in that column's own
`_note`*. Both halves were tested: with the stale patch re-enabled it fails on
`year_built_precision`, and it does **not** fire on the `site_type` and `status` patches, whose
whole purpose is to move prose into a note column. The first version of it did fire on those —
a wrong check, fixed rather than worked around, per RULE 4.

## After importing

```bash
npm run data:build && npm run data:validate
npm run data:check:live      # expect zero row drift
```

Then, in order, the derived builds — the snapshot alone is not the dataset:

```bash
npm run data:build:provenance      # REQUIRED: provenance.json covers 169 and has no entry
                                   # for Shah Gohar Peer or Mian Qurban Ali Shah. Skipping this
                                   # reproduces the 18 August failure that broke a deploy.
npm run data:export                # KG + JSON-LD + RDF
npm run verify                     # includes data:validate
```

**`data:validate` will then fail on purpose, and clearing it is the last step.**
`scripts/data/validate-survey-provenance.mjs` lists Shah Jamal, Peer Makki and Mauj Darya
Bukhari in `KNOWN` *because they currently fail*. Once this import lands they pass, and the gate
fails on the stale allowlist instead and says so. **Delete all three entries from `KNOWN`.**
That is the whole maintenance burden, and it is deliberate — a recorded exception that no longer
describes a real failure outlives everyone who remembers why it was written.

**A note on the 16 → 19 figure, because it is spent and it was never 16.** The 5 September
instructions say `support_level = Field-verified` and `info_level = Full` go 16 → 19 on import.
Measured 10 September: the **live sheet already reads 19** on both — that half of the patch
reached the sheet, and only its `qa_note`, `silsila` and date columns did not. The **shipped
snapshot reads 14**, which is what the site renders today, so the move a reader will see is
**14 → 19** and `data:build` is what makes it, not this import. (14 + the 3 rows this patch
attributes = the 17 surveyed rows that are shipped at all; the other 2 of 19 are the drift rows.)
`/about` recomputes these from the shipped data on every load, so no number needs editing by
hand.

## Regenerate at any time

```bash
python3 pipeline/build_consolidated_import.py --dry-run   # every check, writes nothing
python3 pipeline/build_consolidated_import.py
```

It fetches the sheet itself, so re-running after any sheet edit rebases the merge on what is
actually live. If the sheet is no longer 171 rows × 44 columns it refuses to run rather than
guessing.
