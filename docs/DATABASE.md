## Security

- The server listens on **localhost only** (`listen_addresses = 'localhost'`); `pg_hba.conf` admits
  only 127.0.0.1/::1, with **scram-sha-256** passwords. Nothing faces the network.
- **Roles.** `shrines_owner` (NOLOGIN) owns every table; migrations run as it. `shrines_editor`
  may change content (`sites`, `site_images`) and read history, and cannot alter structure or
  history. `shrines_reader` may read. Logins: `rauf` (editor), `shrines_export` (reader: the
  export), `postgres` (superuser: setup, import, backups only). Each person gets their own login
  (`setup_cluster.py --add-editor NAME`), so the history says who changed what.
- Passwords are generated by `setup_cluster.py`, written only to the pgpass file, never printed,
  never in the repo. `DATABASE_URL`-style strings with a password are not used anywhere.
- **History.** Every insert, update and delete on `sites` and `site_images` is written to
  `audit.change_log` (who, when, the row before and after, transaction id) by a `SECURITY DEFINER`
  trigger; editors can read it and cannot write, change or delete it.

Verified 30 October 2026: an editor cannot `ALTER TABLE` ("must be owner"), cannot delete from the
history ("permission denied"); the export login cannot update; a category outside the six is
refused by its CHECK; an edit by `rauf` appears in the history as `rauf`.

## Schema (`pipeline/db/migrations/`)

`sites` holds **every** sheet column, internal ones (`qa_note`, `needs_review`, `flags`) and the
legacy fallbacks (`legacy_category`, `legacy_founded`, `legacy_sufi_saint`) included: this is the
master, and what the public sees is decided at export. Values are stored **exactly as entered**;
an empty cell is NULL; coordinates are unconstrained `numeric`, which keeps the digits as typed.
`geom` is generated from them, with a GiST index. `description` is one value: the sheet's
`Description 2..5` (a 50,000-character cell limit) are joined by the site's own rule
(`joinContinuationColumns`). `site_images` has one row per image with its slot (`position` 1-16;
Image 1 is the lead image). `sheet_row` keeps the sheet's order.

CHECKs only on the controlled vocabularies in CLAUDE.md: `category`, `status`, `info_level`,
`support_level`, plus the id format, Pakistan's bounding box, and latitude/longitude both or
neither. All 489 rows satisfied them without a single edit. `year_built_precision` and
`figure_type` hold qualifying prose and are deliberately unconstrained.

**Since migration 0002 the tables live in schema `archive`**, not `public`, with row-level security on and
policies only for the archive's own roles. On Supabase, `public` is published through the hosted REST
API to the `anon` key; `archive` is not, and those roles are revoked from it as well. Connections set
`search_path = archive, public, extensions` (`db.py`; `extensions` is where Supabase keeps PostGIS).

**Changing the schema:** add `migrations/000N_name.sql` and run `python pipeline/db/migrate.py`.
Never edit an applied migration; the runner stores each file's SHA-256 and refuses.

## The guarantees, and how each is checked

| Guarantee | Check |
|---|---|
| The database holds exactly what the sheet held | `import_sheet.py` reads every cell back and compares before it commits; one transaction, so a mismatch loads nothing |
| The site build sees no change | the export, parsed by papaparse with the build's own options and join rule, equals the sheet's parse: **true, 489 rows** (30 Oct 2026) |
| A reload can never overwrite people's edits | `--replace` refuses once `audit.change_log` holds any change not made by the importer |
| A renamed or new sheet column is never dropped silently | the import refuses unknown or missing headers until `sheetmap.py` is changed on purpose |
| TSV cannot sneak in | the import refuses a tab-separated header (RULE 3) |
| Backups restore | every nightly run restores its dump into a scratch database and compares a fingerprint (row hashes, history count, migrations) with the live one; exit 1 and `FAILED` in the log otherwise |
| WAL archiving is working | each backup run checks the server's last archived segment is actually in `~/pgbackup/wal` and that no newer failure is recorded |
| Point-in-time recovery works | drilled 30 Oct 2026: base backup + WAL restored into a scratch server on port 5433; same 489/261/750 counts and identical `sites` hash as live |

## Backups

Three layers: the **WAL archive** (each 16 MB segment copied as it closes, at least every 15
minutes: at most ~15 minutes of edits can be lost), weekly **base backups** (with the WAL, recovery
to any moment), and nightly **logical dumps** (`pg_dump -Fc`, SHA-256 beside each). Retention: 30
dumps, 4 base backups; WAL older than the oldest kept base backup is pruned by
`pg_archivecleanup`.

**Restore from a dump:** `createdb -h localhost -U postgres shrines_restored` then
`pg_restore -h localhost -U postgres -d shrines_restored --no-owner <dump>`.
**Point-in-time:** extract `base.tar.gz` into an empty data directory and `pg_wal.tar.gz` into its
`pg_wal/`, create `recovery.signal`, set `restore_command = 'copy "C:/Users/g16/pgbackup/wal/%f" "%p"'`
(and `recovery_target_time` if you want a moment other than the latest), start it.

**Scheduling** is `pipeline/db/windows/install_tasks.ps1` (start at logon; nightly backup 02:30;
weekly base backup Sunday 03:00; missed runs happen at the next chance). It registers user-level
scheduled tasks; run it yourself once (see below). **Not yet registered** as of 30 October 2026.

## Gotchas (each cost real time)

- **`postgresql.conf` eats single backslashes.** `archive_command` written with Windows paths
  became `C:Usersg16pgbackupwal%f`: a path relative to the data directory, so the server
  reported every segment *archived* while the archive folder stayed empty and the files piled up
  inside `pgdata` under mangled names. Use forward slashes. The backup run now checks the file
  is really there, because the server's own counter said everything was fine.
- **The EDB installer through winget fails silently without admin** (exit 1, a 57-byte log). The
  zip binaries need no installer and no admin.
- **pgpass entries are per port.** A scratch server on 5433 has no entry, and psql then waits for
  a password prompt that never comes.

## Cutover: from the sheet to the database

Until cutover, the **sheet is still production** (RULE 3) and the database is refreshed from it
with `import_sheet.py --from-sheet --replace`. The steps, none taken yet:

1. **Parallel run.** Re-import from the sheet and run `--verify-against` daily for a few days; it
   must stay identical.
2. **Freeze the sheet.** Make it view-only for everyone; record the moment here. From then on no
   one edits the sheet.
3. **Last import, then edit only the database.** The first edit by a person locks `--replace`
   for good.
4. **Point the build at the export.** `scripts/data/build-dataset.mjs` reads `CSV_URL` with
   `fetch`; it needs a local-file input (the export), and the runtime `CSV_URL` in
   `src/lib/data/constants.ts` must stop fetching the sheet so the site uses the shipped snapshot.
   This touches the website's code and is a separate, reviewed change.
5. **Keep the sheet** as a read-only historical copy; do not delete it.
